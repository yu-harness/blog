## 一条最简单的指令

我给一个自己写的 Agent 下了这样的指令：

> 在这个目录创建一个 py 文件，输出 hello word

它把下面这段原样打印了出来：

```
<|DSML| calls>
<|DSML| invoke name="write_file" path="hello.py"><content>print("hello word")
</content></tool>
```

文件没有创建。

它也没有报错。任务正常收工，`attempts = 1`。

也就是说：**这个 Agent 报告"做完了"，实际上一步都没动。**

## 先定位失败发生在哪一步

排查范围可以缩得很小，因为每次运行都会在 `.pico/runs/<run_id>/` 留下两份工件。

`report.json` 里，`attempts` 是 1，`final_answer` 就是上面那段文本——说明模型这一轮的输出，被当成了最终答复。

`trace.jsonl` 里的事件链是：

```
run_started → prompt_built → model_requested → model_parsed
  → checkpoint_created → run_finished
```

少了 `tool_executed`。

**模型的输出被解析完了，然后什么都没执行。** 从 `model_parsed` 到 `run_finished` 之间，那次工具调用凭空消失了。

## 为什么它会消失

工具调用的格式约定写在系统提示词里：要求模型输出 `<tool>{"name": ..., "args": ...}</tool>`。

而解析函数的判定链只认字面量 `<tool>` 和 `<tool`。模型这次吐的是 `<|DSML| invoke ...>`，两个都不匹配，也没有 `<final>`，于是落到兜底那条规则：

> 非空文本 = 最终答案

一次工具调用被当成最终答案吞掉了。

这里最该讲清楚的是**失败的方向**：它没有报错，它是"没解析出来"被当成了"模型给了答案"。解析失败和正常收工走了同一条路——所以你从日志上看不出任何异常。

## 模型那边其实很努力

`<|DSML| ...>` 是训练期的特殊 token 风格，不在提示词教的格式里。

有意思的是结尾那个 `</tool>`——它是从提示词里的示例抄来的。模型想调工具，只是格式学串了，顺手把示例的结尾也抄了上去。

## 这暴露的问题比这个模型大

如果结论停在"V4.1-Flash 有个坑"，那这篇文章只值一个 issue。

往上抽一层：**工具调用的格式约定写在提示词里，等于把控制权交给模型的输出习惯。**

模型的实际输出格式由训练决定。提示词能做的只有"请求"，做不到"约束"。所以只要格式约束留在提示词里，每换一个模型就要重新赌一次。这次是 `<|DSML|`，下次可能是别的写法，你不可能穷举。

而每次漏网都会以静默的形式出现——因为兜底分支天然倾向于把"不认识的东西"当成正常输出。

## 该由谁负责

格式约束是协议问题，不该由提示词承担。

- **交给协议**：API 原生的 function calling / `tools` 参数。格式由接口保证，模型只负责选哪个工具、传什么参数
- **留给提示词**：意图表达、任务边界、约束条件

判断一个 Agent 靠不靠得住，可以看它把格式约束写在哪儿。

## 我实际改了什么

只加了兼容层：把 `<|DSML| invoke ...>` 翻译成标准结构，再加一条保守规则——"看起来想调工具但格式没认出来"的时候，让模型按正确格式重写一次。

六个 case 都过了，包括"纯文本答案没有被误伤"。

但这是止血，不是正解。正解是上面那条分工。

## 一句话

解析函数的兜底分支，是静默失败最容易藏身的地方。"没解析出来"和"模型给了答案"，必须是两条路。
